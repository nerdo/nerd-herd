    nerd-herd engine: one state core for Agents and Spaces, many hosts

    Today the Agents mod keeps part of its state in the Herdr mod layer (src/mod/agents/): which statuses are folded, when each session entered its status, which sessions got their starting point, the version control labels, and what each click does. Only end-to-end walks in a running window reach that code, and a full walk run takes about 11 minutes. This spec moves that state into one engine that takes plain inputs and returns the view, the next state, and the effects to carry out. Herdr becomes one host that feeds the engine and carries out its effects. A text host, and later a command-line or mobile host, can feed it the same inputs. State behavior is then tested in unit tests that run in about a second, and walks check only what the person sees.

    The same Agents, through one engine

    Claims
    1. The engine computes the same Agents sections and cards from Herdr's data as the mod showed before
    2. A click in Agents reaches the engine as a command and Herdr carries out what the engine asks for
    3. Folds and the sort and time in status read back after a restart as before

    Dannel opens Herdr after the move. The Agents section shows Done, Blocked, Working and Idle pills with the same cards, times and version control labels as the day before, because the Herdr host hands the engine the same agents, spaces, terminals and groups, and draws the view it gets back. Dannel clicks the Idle pill to fold it. The click becomes a fold command, the engine returns a view with Idle folded and asks for the folded statuses to be saved, and the Herdr host saves them. Dannel quits Herdr and opens it again, and Idle is still folded.

    The same Spaces, through the same engine

    Claims
    1. The engine computes the same Spaces groups and rows from Herdr's data as Spaces showed before
    2. A Spaces action reaches the engine as a command and Herdr carries out what the engine asks for
    3. Spaces no longer depends on a copy of Herdr's Spaces mod

    Dannel opens Herdr after Spaces moves. The Spaces section shows the same groups, machines and spaces with the active space outlined, now drawn by the Herdr host from the engine's view instead of by a patched copy of Herdr's Spaces mod.     Working out a feature without a window

    Claims
    1. A behavior of the Agents state is tested by giving the engine inputs and reading what it returns without a Herdr window
    2. The engine imports nothing from Herdr or from any host

    Dannel asks for a new rule: a Blocked session should stay at the top of its group even when the group is folded. The rule is stated as engine inputs (Herdr's data with a blocked session in a folded group) and the view expected back, and its test fails in under a second. Once the engine passes it, one walk checks that the window draws the mark. Nothing in the engine can reach Herdr by accident, because the boundary check fails the build when the engine imports from a host.

    A second host

    Claims
    1. A text host prints the same Agents list from the same inputs

    To show the engine depends on no host, a small text host reads a saved snapshot of Herdr's data and prints the Agents list as text: each section, then its cards with title, place, machine, time and version control. It prints the same list the Herdr host draws from the same snapshot. A command-line or mobile host later maps its own inputs the same way.

    Questions

    Whether to extract the engine

    Question
    Should the Agents state move into a host-independent engine, so features are worked out with fast tests and walks only check the output?
    Resolution
    Yes, as its own spec after the Agents mod spec closes (the user, 2026-11-20: "extract the state engine as an agnostic piece of this ... map those inputs to where they need to go and interpret those outputs in the specific domain"; "draft the engine spec while we wait for this one to close").

    Engine shape

    Question
    Is the engine one pure step function, or an object that holds its state?
    Context
    A host calls the engine on every Herdr change, clock tick, command and version control reading.
    Options
    • Pure step: step(state, input) → { state, view, effects }. Every test is one call with no setup; the host keeps the state between calls.
    • Object: engine.send(input) with the state inside. Hosts are simpler; tests need an engine per case and read state through methods.
    Resolution
    Pure step: step(state, input) → { state, view, effects }, with a five-line helper that holds the state for hosts that want an object (the user, 2026-11-20: "do all your recommendations").

    Spaces in scope

    Question
    Does this spec move Spaces' state into an engine too, or Agents only?
    Context
    Agents is a mod nerd-herd wrote. Spaces is Herdr's own mod, vendored and patched (src/mod/vendor/herdrSpaces.js), with its state kept inside Herdr's class. That difference is how each was built, and it says nothing about what the engine owns.
    Resolution
    Both. The engine owns every idea in Agents and Spaces with its own models, analogous to Herdr's but self-contained, and the Herdr host is a separate layer that maps Herdr's data in and draws the engine's view out (the user, 2026-11-20: "we should own all the ideas around it and there should be a separate layer that kind of processes it through Herder"; "in my mind they're actually the same idea"). The Herdr host then draws Spaces from the engine's view, so the vendored Spaces file and its patches retire and Herdr's later Spaces changes no longer arrive through the vendor script.

    Second host in this spec

    Question
    Does this spec build the text host, or leave every second host for later?
    Context
    Unit tests already call the engine without Herdr. A host that prints text from a snapshot is a second real caller, so a Herdr-only assumption in the engine shows up now rather than when a mobile host starts.
    Options
    • Text host from a snapshot file: small, runnable from the terminal, no live data.
    • Command-line host on live herdr-core data (hc): more useful day to day; adds reading herdr-core outside Herdr, which no spec has looked at yet.
    • No second host: the unit tests stand in for one.
    Resolution
    The text host from a snapshot file is built in this spec. A live command-line host gets its own spec (the user, 2026-11-20: "do all your recommendations").

    Engine location

    Question
    Does the engine live in this repository's src/core, or in a package of its own?
    Context
    A mobile app or another repository would import a package; nothing imports it from outside yet.
    Options
    • A folder in src/core/engine/ with its own boundary zone: no packaging work now; moving it later is a folder move.
    • A package now (packages/agents-engine): ready for outside hosts; adds a workspace and a build for one consumer.
    Resolution
    A folder in src/core/engine/ with its own boundary zone. It becomes a package when a host outside this repository starts (the user, 2026-11-20: "do all your recommendations").

    What the view holds

    Question
    Does the engine's view name looks (purple outline, tint colors, sizes), or only meanings (focused, folded, status, attention counts) that each host draws in its own way?
    Context
    A text host has no colors, and a mobile host has its own theme. The more the view decides, the more a unit test covers; the more it names looks, the less it fits other hosts.
    Options
    • Meanings only: each host maps a meaning to its look (Herdr: focused → purple outline).
    • Meanings and looks: the view carries colors; other hosts ignore them.
    Resolution
    Meanings only. Each host maps a meaning to its own look, such as Herdr drawing focused as the purple outline (the user, 2026-11-20: "do all your recommendations").

    Process Flow

    Module Definitions

    Engine

    Responsibility
    Turns the current state and one input into the next state, the view, and the effects a host must carry out.
    Owns
    For Agents: the sort, folded groups and statuses, when each session entered its status, which sessions have their starting point, the version control labels, and what each command changes. Today these live in src/mod/agents/app.ts, main.ts and herdrAgents.ts. For Spaces: the groups and what holds what, the active space, folded groups, space colors, reconnecting machines, a drag in progress, which dialog is open, and what each Spaces command changes. Today the group parts live in src/core/groups and the rest inside Herdr's class in src/mod/vendor/herdrSpaces.js.
    Delegates
    Arranging rows to the session list model (src/core/sessions/sessionList.ts); the Done rule to the Done ledger; time text to statusTime.ts; label text to src/core/jj/vcsLabel.ts; group looks to src/core/groups/groupLook.ts.
    Input AgentsInput
    One of: Herdr's data (sessions, spaces, machines, focus), a clock tick, a typed Agents or Spaces command, a version control reading, or saved values at start.
    Output AgentsStep
    The next state, the view (Agents rows and Spaces rows, with meanings), and a list of effects.

    Herdr host

    Responsibility
    Feeds Herdr's data, clicks and the clock to the engine, draws its view in Herdr, and carries out its effects with Herdr's APIs and hc.
    Owns
    Reading Herdr (agents(), spaces(), terminals(), panes()), the command text format (fold-status:{json} and the rest), drawing with gpui-kit, and storage in localStorage and shared state.
    Delegates
    Every decision about state and what shows to the engine.
    Input Herdr APIs
    Herdr's data, commands, the timer.
    Output Elements and Herdr calls
    The drawn Agents and Spaces sections, and Herdr commands for each effect.

    Text host

    Responsibility
    Prints the Agents list as text from a snapshot of Herdr's data.
    Owns
    Reading the snapshot file and the text layout.
    Delegates
    Everything else to the engine.
    Input Snapshot file
    JSON holding the same data the Herdr host gives the engine.
    Output Text
    The sections and cards, one line per row.

    Validation Boundaries
    • Host to engine: every input is typed. A host parses its own wire format (Herdr's command text, a snapshot file) and passes only typed inputs. Text that cannot be read never reaches the engine; the host reports it, and the next command still applies.
    • Saved values handed in at start are external data: another version or a hand edit may have written them. The engine reads them through its own schema and counts an unreadable value as never saved.
    • Labels and titles from Herdr keep the rules of the Agents mod spec: nerd-herd.handled is a whole turn number or no label, and a title is shown as text.
    • Engine to host: effects are data. The engine never calls a host, so a host may batch, retry or drop an effect without the engine knowing how.

    Ambiguity Resolution

    "Engine" means the code that holds the state of Agents and Spaces and decides what shows. "Host" means the code around it that reads a platform's data and draws or prints the view. Herdr is the first host.

    "Same as before" in the first journey is measured by the Agents walks: they run against the engine with their expected values unchanged. Changing an expected value during this spec is a behavior change, and it needs the user's decision first.

    "Same as before" for Spaces is measured by the Spaces walks the same way. Herdr's Spaces mod does things no walk checks today, such as dragging and reconnecting a machine. Before the Spaces phase starts, those behaviors are listed from Herdr's Spaces file and each gets a test, so nothing is dropped because no walk caught it.

    The view carries meanings only, as resolved in "What the view holds". Each host decides how a meaning looks.

    When

    Then

    A session in terminal t1, another pane focused
    When
