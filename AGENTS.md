# AGENTS.md

Instructions for coding agents working in nerd-herd. What the project is and how to run it is in [README.md](README.md). Read it first.

## Rules

These rules protect the person's own Herdr, their machines, and their screen while you work.

1. **Run every Herdr window you start under a test home.** Set `HERDR_APP_HOME` to `"$PWD/.hw-home"`, run from the repository root (version control ignores that folder), on every `bun run herdr:install`, every `herdr-app do`, and every other command that starts or talks to a Herdr window. The person's own home is `~/.config/herdr-app`. `bun run herdr:install` without `HERDR_APP_HOME` installs into it, so run that only when the person asks you to install the mod for them.
2. **Quit every test window you start, including when the work stops early.** Run `HERDR_APP_HOME=<that test home> bun scripts/stop-window.ts`. Then run `HERDR_APP_HOME=<that test home> herdr-app status`, and keep its output in your reply or your session log. It prints "no Herdr window at …" once the window is gone.
3. **Drive Herdr through commands, never through the pointer or the keyboard.** Use `herdr-app do`, the walk harness (`e2e/support/herdr-window.ts`), and the mod's own command strings. Clicking, dragging, and typing on the person's display are for the person's own hand check. Write what needs a hand check into the spec's end-user validation table, marked "needs pointer".
4. **Never create, rename, move, or close a space, tab, or terminal, in a test or while debugging, unless the person asks for that change.** Every Herdr window, test windows included, shares the person's real herdr-core, so a changed space is the person's real space. Tests and debugging may only read spaces and machines, for example with `hc machine ls --json`.
5. **Do not read secret values.** A secret is any token, password, key, or credential, wherever it is stored. When you need one, name where it lives and let the person supply it.
6. **Write the failing test before the code.** Run it, and keep the runner output that shows it failing on a value the code produced. Then write the code, and keep the output that shows it passing. Keep both outputs in your reply or your session log. When you add a test, and the code it checks is already written, first change that code to a deliberately wrong version and keep the output that shows the test failing.
7. **Keep `bun run check:all` and `bun run test:e2e` passing before every commit.** Quote the pass and fail counts from their output when you report.

The reflex these rules catch: a test window looks like a sandbox, so the shared herdr-core and the person's screen behind it are easy to forget. A command that works against the test home is not proof that it left the person's own setup alone.

## How the code is arranged

- `src/core` holds the logic, and it imports nothing from Herdr. A behavior belongs here when it can be stated without Herdr. `bun run check:boundaries` fails when a core file imports from `src/mod`.
- `src/mod` connects the core to Herdr: the view, the dialogs, and the adapters.
- `src/mod/vendor/herdrSpaces.js` is generated by `scripts/vendor-spaces.ts`. Change that script, never the generated file. The file stays under the Apache License 2.0.
- Keep each source file within biome's line limit (`noExcessiveLinesPerFile`, 300, in `biome.json`). biome only warns, so `check:all` still passes: read the lint output, and split a file it warns about by subject. Files biome does not lint (`src/mod/vendor/**/*.js` and `types/herdr`) are outside the limit.
- The mod reads and writes its saved data through commands of the form `<action>:<JSON>`, applied in `src/core/commands/applyCommand.ts`. The walks send the same commands.

## Specs

- Every behavior comes from a spec in `docs/specs`. The folder names the stage: `ideas`, `drafts`, `finalized`, `in-progress`, `completed`, or `abandoned`.
- The person moves a spec between stages. Do not move one unless the person asks.
- A test cites the spec statement it checks, as a path with an anchor pinned to a commit, in the form `docs/specs/<stage>/<spec>.html#<anchor>@jj:<commit id>`. Use the path the spec has at that commit; older citations keep the path the spec had when they were written.
- A behavior found during the work gets a row in the spec's end-user validation table, with how it is checked.

## End-to-end walks

- Each walk makes a `new HerdrWindow()` and calls its `start()` to open its own Herdr window in `.e2e-home`, which `start()` deletes and recreates, sends commands, and reads the window's text with Apple's Vision framework (`.e2e-bin/read-text`).
- A walk sets every input it depends on: the window size, light appearance, and the saved data. Do not rely on the person's settings.
- The walks run one at a time (`workers: 1`), because they share one display.
- Screenshots land in `.e2e-bin/shots`. Look at them when a reading surprises you, before you change a test.

## Version control

This repository uses jj (Jujutsu) colocated with git. Make changes with jj, not git.

- Commit at each checkpoint where `bun run check:all` and `bun run test:e2e` pass, one unit of work per commit, with a Conventional Commits message such as `feat(spaces): reload a group's banner images`.
- Do not push. Pushing is the person's decision.
